## 1. 方法：6 个位平面设计，而不是 64 个单点设计

原本打算造 64 个 `INIT=2^k` 的设计。更好的办法是用**位平面编码**：只造 6 个，
第 k 个设计的 INIT 让「索引 i 的第 k 位为 1」的那些位置为 1：

| k | INIT 值 |
|---|---|
| 0 | `0x5555555555555555` |
| 1 | `0xCCCCCCCCCCCCCCCC` |
| 2 | `0xF0F0F0F0F0F0F0F0` |
| 3 | `0xFF00FF00FF00FF00` |
| 4 | `0xFFFF0000FFFF0000` |
| 5 | `0xFFFFFFFF00000000` |

每个设计与基线 `_full8.bit`（INIT=1）逐位差分，得到该设计的置位格集合。
对任意一个格，`索引 = Σ_k (该格在第 k 个差分中出现) << k`。

**6 次综合实现了 64 次的效果**（约 20 分钟 vs 约 80 分钟）。

## 2. 结果：64 个 INIT 位落位

数据格共 64 个（排除 word 50 的 ECC 变化），映射完整无重（`clb_init_map_x12y20.json`）：

```
INIT[00] -> (31786, 40, 15)      INIT[01] -> (31786, 40, 7)
INIT[02] -> (31784, 40, 15)      INIT[03] -> (31784, 40, 7)
INIT[04] -> (31786, 40, 11)      INIT[05] -> (31786, 40, 3)
INIT[06] -> (31784, 40, 11)      INIT[07] -> (31784, 40, 3)
INIT[08] -> (31786, 40, 13)      INIT[09] -> (31786, 40, 5)
...
```

结构：所有 INIT 位都在 **word 40（= 2*(20%50) + 0，y=20 的 parity 0 字）**，
分布在 **frame 31784 / 31785 / 31786**（= block base 31716 + 68/69/70）三个帧上。
而旧表（`site_frames`）说 INIT 在 frame 31786/31787 且 64 位分散在 4 个帧 —— **旧表是错的**。

```

```

11 个字节分别是：

* **7 个字节在头部**：文件日期 `2026/11/02` → `2026/11/04`、时间 `18:43:26` → `21:02:34`

## 5. 还没解决：尾部 CRC 算法
