# T8：位流改写器 —— 改位 + 重算 ECC + 反解码验证

日期：2026-11-04
脚本：`v7re/scripts/ecc_model.py`（建 ECC 数据项模型）、`v7re/scripts/bitgen.py`（改写 .bit）

## 1. ECC 数据项模型

`ecc_model.py` 从 9 个 bitstream 的 739 个「数据非零」帧建方程，用「迭代剔除法」把被
行边界 marker 污染的方程剔除：

```
初始方程 739 → 第 1 轮（秩 200，矛盾）保留 575，剔除 164
              → 第 2 轮（秩 130，无矛盾）保留 562，剔除 13
              → 第 3 轮（秩 124，无矛盾）保留 562，剔除 0
```

收敛后得到 124 个位置的签名 `L[p]`（p = word*32+bit），写入 `v7re/steps/ecc_model.json`。
含义：某帧数据的置位集合为 S 时，`ECC(data) = XOR_{p∈S} L[p]`。

## 2. 跨设计验证（对照 Vivado 真实产物）

用 `L` 预测两个真实 bitstream 在**同一帧**上的 ECC 差：

| 对比 | 相符 | 不符 | 含未采样位置 |
|---|---|---|---|
| c0 vs c1 | 0（两者全零帧完全相同） | 0 | 0 |
| c0 vs c3 | **59** | **0** | 9 |
| c0 vs c4 | **46** | **0** | 12 |
| c0 vs full8 | **56** | **0** | 92 |
| c0 vs d2 | 62 | 1 | 34 |

即：只要改动的位都在模型覆盖范围内，ECC 差**零误差**；唯一的 1 例不符落在边界 marker 帧上。

## 3. 改写器

`bitgen.py`：
- 接受 `--set frame:word:bit=0/1`；
- 直接按字下标改 `.bit` 的 payload 字节（不动包头、不动尾部包）；
- 受影响帧的 `word50`：`低 13 位 ^= XOR L[p]`，高位 marker 原样保留；
- 遇到模型里没有的位置**直接报错退出**，不做猜测。

### 无改动测试（逐字节）

```
_c0.bit        sha256 B777B900BF0AF1C8223935A66F076B06453174F1705BA9294EDB59CF84DFCC6F
_c0_noop.bit   sha256 B777B900BF0AF1C8223935A66F076B06453174F1705BA9294EDB59CF84DFCC6F
```

完全一致 —— 写回路径没有引入任何字节级扰动。

### 真实改动测试：删掉一条 PIP

目标：`INT_L_X8Y20` 的 `WR1END2 ->> IMUX_L5`（4 格 pattern，唯一可判），
其绝对位置为 `(31770,41,8) (31775,41,9) (31776,41,9) (31777,41,9)`。

把 4 位清零后，文件差异恰为 4 个数据位 + 4 个 `word50`：

```
frame 31770 word 41: 00004184 -> 00004084   word 50: 0000086f -> 000000e7
frame 31775 word 41: 00540216 -> 00540016   word 50: 000000e7 -> 0000186e
frame 31776 word 41: 7c7ed67e -> 7c7ed47e   word 50: 0000101f -> 00000896
frame 31777 word 41: 0256ae7e -> 0256ac7e   word 50: 0000086a -> 000010e3
```

没有任何其它帧被波及。

### 反解码验证

对改后文件重新跑解码：

| 文件 | 解码 PIP 总数 | `INT_L_X8Y20` IMUX | 含 `IMUX_L5` |
|---|---|---|---|
| `_full8.bit` | 282 | 108 | 是 |
| `_full8_edit.bit` | 279 | 105 | **否** |

删掉的 PIP 不再出现在解码结果里，其余结构不变。

## 4. 能力与边界

已具备：**改位 → 自动维护帧级 ECC → 反解码确认** 的闭环。
未验证：把改后 bitstream 真正加载到器件（无硬件），以及 Vivado 侧是否接受该文件。

ECC 覆盖的 124 个位置对于「mux 区 PIP 的增删」已经够用（48 条 IMUX 全部 4/4 覆盖），
但更大的改动（CLB INIT 全 64 位、BEG 长线族）仍需扩充模型——扩充方式就是再造设计、重跑
`ecc_model.py`，方法已经自动化。


## 5. 决定性验证：用 c0 生成 c3（对照 Vivado 产物）

c0 与 c3 是两个真实设计（c3 的 CE 经 FAN 走线），逐帧比较共 94 个数据位不同。
把其中 **78 个落在 ECC 模型覆盖范围内**的位，用 `bitgen.py` 从 `_c0.bit` 写进去，
再与 Vivado 自己产出的 `_c3.bit` 逐帧比较：

```
可写入改动 78 位，影响 64 帧
生成文件与 Vivado 产物不同的帧数: 4
  这些帧: [32500, 32574, 32606, 32607]
  其中属于「含未覆盖位」的: [32500, 32574, 32606, 32607]
  其余（模型算错）: []
逐帧完全相同: 50172 / 50176 (99.99%)
```

关键点：

* **模型算错的帧 = 0**；
* 仅有的 4 个不同帧，全部是「含未覆盖位置」的帧（16 个未覆盖位的分布正好落在这 4 帧）；
* 也就是说：**凡是 ECC 模型覆盖到的改动，生成结果与 Vivado 逐字节一致**，
  包括这 64 个受影响帧的 word50。

补全那 16 个位置（word 2/3/4/5/14/16 的若干 bit）后，这条链路就能做到 100% 位级一致。
