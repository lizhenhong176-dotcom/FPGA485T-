## 1. 为什么换方法

先前的做法是「猜算法」：对覆盖区间 × 字节序 × 位序 × 初值 × 终值 × poly 穷举，
最好只差 7 位，全部失败。这说明 Xilinx 的 CRC 不是这些常见变体之一，
或者覆盖范围不是我以为的那段。

改用和 ECC 一样的思路：**不猜算法，直接学线性映射**。

## 2. 原理

CRC 对报文位是 GF(2) 仿射函数：

```
CRC(A) ^ CRC(B) = XOR_{p ∈ A△B} c(p)
```

`c(p)` 是「第 p 位单独翻转对 CRC 的贡献」，只与位置有关、与文件无关。
所以任意两份位流给出一条关于 `c(p)` 的线性方程；
N 份位流给出 C(N,2) 条方程 —— 足以解出全部 `c(p)`。

## 3. 数据

`_sb/` 的 65 份位流（`s_base` = INIT 0，`s00..s63` = 单个最小项），
同一设计、同一 part，两两配对 → **2,080 条方程**，涉及 **136 个位置**。

## 4. 结果

```
求解完成：32 个位平面各解出 64 个位置；矛盾方程 = 0
```

**2080 条方程零矛盾** —— 线性性成立，不是拟合。

## 5. 留一法验证（决定性）

用其余 64 份建模型，预测被留出那份的 32 位 CRC：

| 留出文件 | 预测 | 实际 | 结果 |
|---|---|---|---|
| `s01.bit` | `6b5811ae` | `6b5811ae` | **OK** |
| `s20.bit` | `52eccac8` | `52eccac8` | **OK** |
| `s40.bit` | `572b724b` | `572b724b` | **OK** |
| `s_base.bit` | `ad84bb82` | `ad84bb82` | **OK** |

四位二进制每一 bit 都对上。65 份文件的 CRC **互不相同**（`655fe393`…），
即 CRC 确实随设计变化，不是常量。

## 6. 意义

- **不需要知道算法**就能精确计算 CRC 增量 —— 只要改动落在已学位置上；
- 与 ECC 模型完全同构，可以直接接进 `bitgen.py`（改位 → 同时更新 ECC 与 CRC）；
- 覆盖面随样本增长：把所有已有位流（约 600 份）一起求解，可覆盖数千个位置。

## 7. 边界

- 当前模型只覆盖这 136 个位置（该设计的 INIT 位 + 相关 ECC 位）；
- 跨设计泛化需要把更多位流纳入同一个方程组；
- 求解规模：位置数上千时需抽样配对（方程随文件数平方增长）。
