# T14：INIT 映射的平移性检验（SLICEL 成立，SLICEM 不成立）

日期：2026-11-05
目的：回答「T13 的表能不能推广到其它行/列」。

## 1. 实验结果一：帧偏移与字公式是通用的

在 `grid_col=6`、`y=8`（离 T13 的 `y=20 / col 19-20` 很远）重做位平面实验（8 次综合）：

| 项 | y=20（T13） | y=8（本次） | 关系 |
|---|---|---|---|
| 块基址 | 31716（col 19）/ 31752（col 20） | 31544 | 由 `clb_blocks[(col, y//50)]` 给出 |
| inst1(SLICEL) 帧 | 31778 = base+26 | 31570 = base+26 | **相同** |
| inst0(SLICEM) 帧 | 31784 = base+32 | 31576 = base+32 | **相同** |
| 字 | 40 = 2*(20%50) | 16 = 2*(8%50) | **公式一致** |

即：**帧偏移（+26…+29 / +32…+35）与 `word = 2*(y%50)+parity` 跨行跨列通用**。

## 2. 实验结果二：SLICEL 的位排列可以平移

用 T13 的 SLICEL 表（`SLICE_X13Y20`），只把帧起点按 `base+26` 平移，去解 y=8 的设计
（`SLICE_X3Y8` 的 A6LUT/B6LUT，INIT 分别为 `0x00000000FFFFFFFF` / `0xFFFFFFFF00000000`）：

| BEL | 解出 | 期望 | |
|---|---|---|---|
| SLICE_X3Y8 A6LUT | `0x00000000ffffffff` | `0x00000000ffffffff` | ✅ |
| SLICE_X3Y8 B6LUT | `0xffffffff00000000` | `0xffffffff00000000` | ✅ |

**SLICEL（inst1）的表是真正通用的**：只要按 base 平移帧号、按 y 算 word，64 位全对。

## 3. 实验结果三：SLICEM 的位排列不能平移

同一 y=8 实验里，`SLICE_X2Y8`（inst0，SLICEM）的 A6LUT 用 T13 的 SLICEM 表解不出来。
于是对该 BEL 重做位平面（本组 8 次综合），得到 y=8 自己的表，与 y=20 的表逐条比对：

```
y=20: idx1 -> (Δf 2, bit 7)      y=8: idx1 -> (Δf 2, bit 15)
y=20: idx0 -> (Δf 2, bit 15)     y=8: idx9 -> (Δf 0, bit 15)
完全相同条目: 0 / 64
```

**帧与字完全一致，但帧内的位排列不同** —— 排列不是常量，随位置变化。

## 4. 结论与影响

| 项 | 状态 |
|---|---|
| 帧偏移 +26…+29（inst1）/ +32…+35（inst0） | 通用 ✅ |
| `word = 2*(y%50) + parity` | 通用 ✅ |
| SLICEL 的 64 位排列 | 通用 ✅（跨 12 行、跨 2 列验证） |
| SLICEM 的 64 位排列 | **不通用**，随位置变化 ❌ |

影响：**CLBLL 全部是 SLICEL**，所以占绝大多数 slice 的 INIT 可以用一张表通吃；
**CLBLM 的 X0 是 SLICEM**，其 INIT 排列需要额外规律或按位置分别测量。

这也解释了 T11 当初为什么会得到「自洽但错」的表：不同 slice 实例的排列本来就不同，
如果一次改多个 LUT 而用同一套假设去切分，必然得到错表。

## 7. 更正（2026-11-05 晚）——本页结论收回

后续做了三件事，结果推翻了第 2、3 节的判断：

1. **SLICEL 那次"平移成功"证据不足**：当时用的 INIT 是 `0x00000000FFFFFFFF` 与
   `0xFFFFFFFF00000000`，这种"半区全 1"的值对位排列不敏感——即使排列错了，
   只要 0–31 与 32–63 不互相越界，解出来还是同一个数。不能算验证。
2. **col 6 的 row 3 / row 8 / row 9 三次独立位平面测量，得到三张互不相同的表**
   （row3 vs row9 相同条目 7/63，row3 vs row8 2/63，row9 vs row8 4/63）。
   三者的帧起点都是 `base+32`（31576），字分别是 6 / 16 / 18 —— 帧与字都对，只有位排列不同。
3. **自校验失败**：用 row 3 自己测出来的表，去解同一位置（`SLICE_X2Y3`）的随机 INIT
   `0xA5A5F0F01234ABCD`，解出 `0x5A5AF0F0213857CE`，**不符**。

第 3 条说明：不是"排列随行变化"这么简单，而是**测量流程本身在这些位置上不可靠**。
最可能的原因：不同构建里 placer 把同一个 `LOC/BEL` 约束的 cell 放到了不同的 slice
（例：`INIT=0` 与 `INIT=1` 时的优化路径不同，SLICEM/SLICEL 的选择可能改变），
于是"位平面"混进了别的 slice 的格子。

## 9. 修正后的做法

每个构建都必须**确认 cell 落在预期的 slice 实例与 BEL 上**，否则该次实验作废：

```tcl
place_design
foreach c {u0} {
  puts "CHK $c SITE=[get_property SITE [get_cells $c]] BEL=[get_property BEL [get_cells $c]]"
}
```

并把 `SITE/BEL` 记进结果，只有全部一致的那组构建才参与建表。
在加上这一层之前，任何"跨位置推广"的结论都不成立。
