# T52：「为什么是 6×4」—— 源类别 × 类别内槽位

日期：2026-11-08
方法：全部本地统计（`v7_law.sqlite` 的 `law_cells`，INT_L，sense=1，64 个 mux 族）。

## 1. 每族 24 个源的类别构成（64/64 族完全一致）

把源名分类：`ROUTE`（方向线，如 `NE2END0`/`SL1END0`）、`LOGIC`（`LOGIC_OUTS_L*`/`GFAN*`）、
`BOUNCE`（`BYP_BOUNCE*`/`FAN_BOUNCE*`）。按「行帧」聚合：

| 行帧 | 源数 | 类别 |
|---|---|---|
| 16 | 4 | ROUTE |
| 17 | 4 | ROUTE |
| 18 | 4 | ROUTE |
| 19 | 4 | ROUTE |
| 20 | 4 | LOGIC 或 BOUNCE |
| 21 | 4 | BOUNCE 或 LOGIC |

**64 个族全部符合**，唯一差别是第 20/21 行谁放 LOGIC、谁放 BOUNCE（32 族一种顺序，32 族另一种）。

## 2. 每族 4 个列 cube 的使用次数（64/64 族一致）

```
行帧使用分布: 每行恰好 4 个源   → (4,4,4,4,4,4)
列 cube 分布: 每 cube 恰好 6 个源 → (6,6,6,6)
```

24 = 6 行 × 4 列，且两个方向都是**严格均匀**的。

## 3. 列的四种 cube（全器件只有这 4 种）

```
{(25)}  {(24)}  {(23,24,25)}  {(22,24,25)}
```

## 4. 结论：6 和 4 分别是什么

- **6 = 源类别数**（4 类方向线 + 1 类逻辑输出 + 1 类 bounce 线）；
- **4 = 每类内部的槽位数**（每类恰好 4 条线可接入这个 mux）。

也就是说，一个 INT tile 的 site 引脚 mux，本质上是一个「**6 类 × 4 槽**」的选择器：

```
16 条方向线  = 4 行 × 4 槽   （8 个方向 × 2 种长度类：X2END 与 XL/XR 1END）
 4 条逻辑输出 = 1 行 × 4 槽   （LOGIC_OUTS_L0/L12/L22 + GFAN0）
 4 条 bounce 线 = 1 行 × 4 槽 （BYP_BOUNCE_N3_2/6 + FAN_BOUNCE2/7）
```

这解释了为什么是 6 行而不是 8 行：**方向线有 8 个方向，但它们在 tile 内只占 4 行**
（一行的 4 个槽里放的是不同方向的线，见 `IMUX_L0` 第 16 行：`SL1END0 / NR1END0 / NN2END0 / NE2END0`）。

## 5. 复用规律的真实含义

- 一个「格子」= (行帧, 位) 或 (列帧, 位)，即一条**字面量**；
- 一个「源」= 1 个行字面量 + 该源所在类的列 cube（1 或 3 个列字面量）；
- **复用 = 同一字面量被多个源引用**：
  - 行字面量被 4 个源共用（每行 4 源）；
  - 列 cube 被 6 个源共用（每 cube 6 源）；
  - 平均 5.56 ≈ 加权结果。

## 6. 仍未解释的部分（诚实标注）

1. **为什么方向线是 4 行而不是 8 行**：现在只能说「8 个方向在 tile 内被折成 4 行、每行 4 槽」，
   具体折叠规则（哪个方向进哪一行、哪一列）**就是源→槽位表**，仍属器件布线事实；
2. **为什么列 cube 是 4 种且权重 1,1,3,3**：未解释；
3. **为什么 LOGIC 与 BOUNCE 两行的顺序在 32/32 族之间互换**：看起来与 mux 在 tile 中的位置有关，
   但还没有可预测规则。

## 8. 后续：LOGIC/BOUNCE 行的 32/32 互换**是可预测的**

把每个 mux 族的「第 20/21 行各放什么类别」列出来：

```
IMUX_L0..L7    → 20=LOGIC, 21=BOUNCE
IMUX_L8..L15   → 20=BOUNCE, 21=LOGIC
IMUX_L16..L23  → 20=LOGIC, 21=BOUNCE
IMUX_L24..L31  → 20=BOUNCE, 21=LOGIC
IMUX_L32..L39  → 20=LOGIC, 21=BOUNCE
IMUX_L40..L47  → 20=BOUNCE, 21=LOGIC

BYP_ALT0..7    → 20=LOGIC, 21=BOUNCE   （全部）
FAN_ALT0..7    → 20=BOUNCE, 21=LOGIC   （全部）
```

即：

```
row20 放 LOGIC  ⟺  (IMUX 编号 // 8) 为偶数
                    或 family 属于 BYP_ALT
76 个 mux 族全部命中（48 IMUX + 16 ALT），0 例外
```

这是本次分析里**第一条能预测族级结构的规则**（不含任何查表）。

## 9. 但「16 条方向线怎么分 4 组」仍是 per-mux 数据

按「同一行帧的 4 条方向线」分组，48 个 IMUX 族给出 **32 种不同的分组**：

```
2 族：{EE2END1, EL1END1, SE2END1, WR1END1} / {ER1END0, NE2END1, NN2END1, WL1END0} / …
2 族：{EE2END1, NR1END1, SE2END1, SL1END1} / {EL1END1, SS2END1, SW2END1, WR1END1} / …
…
```

所以：

- **行的「类」（ROUTE / LOGIC / BOUNCE）与 LOGIC/BOUNCE 的顺序** → 可预测（见 §8）；
- **具体哪 4 条方向线进同一行** → 仍是 per-mux 事实（32/48 互异）。

这条界线很清楚：**类别层面可推，实例层面是布线图**。


## 10. 位对与 parity：完全由 mux 编号决定（48/48）

| idx | minbit | parity | | idx | minbit | parity |
|---|---|---|---|---|---|---|
| 0–3 | 0,8,16,24 | 0 | | 4–7 | 0,8,16,24 | 1 |
| 8–11 | 2,10,18,26 | 0 | | 12–15 | 2,10,18,26 | 1 |
| 16–19 | 2,10,18,26 | 0 | | 20–23 | 2,10,18,26 | 1 |
| 24–27 | 4,12,20,28 | 0 | | 28–31 | 4,12,20,28 | 1 |
| 32–35 | 4,12,20,28 | 0 | | 36–39 | 4,12,20,28 | 1 |
| 40–43 | 6,14,22,30 | 0 | | 44–47 | 6,14,22,30 | 1 |

闭式：

```
g = i // 16 ;  h = (i // 8) % 2
minbit = 8 * (i % 4) + 2 * g + 2 * h
parity = 1 if (i % 8) >= 4 else 0
```

**48 个 IMUX 全部命中，0 例外。** 即：**给定 mux 编号，位对位置与 parity 可以直接算出来，不需要任何表。**
