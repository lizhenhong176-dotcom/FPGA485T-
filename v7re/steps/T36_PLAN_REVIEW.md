## 1. 三方对照结论（一句话）

Codex 的方案在**方法论层面站得住**（层级定义、可证伪三件套、负对照、交付物验收），
但它把「源→槽位」当成只能靠 Vivado 测的东西；**本地离线数据已经能证伪其中两条假设，
并把测量范围缩小到只剩「槽位顺序」一项**。

## 3. 本地实测对 Codex 三条假设的反证

### H1「槽位 = 器件线序 rank」——已证伪（离线，0 个构建）

`routing/out_routing/templates/INT_L.json` 里有 3,737 条 PIP，每个目的 wire 的源列表**是按字母序排列的**：

```
IMUX_L40 的 25 条：
BYP_BOUNCE_N3_2, BYP_BOUNCE_N3_6, EE2END0, EL1END0, ER1END0, FAN_BOUNCE2,
FAN_BOUNCE7, GFAN0, LOGIC_OUTS_L0, LOGIC_OUTS_L12, LOGIC_OUTS_L22, NE2END0, ...
```

严格递增的字典序 ⇒ 模板里的顺序**不携带引脚序号**。按模板索引与实测槽位比对：
64 个 mux 族中「完全对齐」0 族、「部分对齐」20 族（每族仅 1–3 个对了，属巧合）。

### H2「槽位 = 8 方向 × 最近端线枚举」——强反证（离线）

按方向前缀给源分类，统计其在 64 个 mux 族中占据的槽位：

| 类别 | 出现过的槽位数 | 例子 |
|---|---|---|
| `EE` | 8 | (1,1) (2,1) (3,0) … |
| `NE` | 8 | (0,0) (3,0) (1,1) … |
| `BYP` | 4 | (5,0) (5,1) (4,0) … |

若槽位由「方向 + 最近端线」决定，同一方向的源应当落在固定槽位；实际每个方向横跨 4–8 个槽位。

更硬的证据：**同一条具体导线在不同 mux 里换槽位**。

```
互斥源名 122 个；始终同槽 0 个；跨族变槽 122 个
   EE2END0   出现在 12 个 mux 族，槽位跨 (0,0) (0,1) (1,0) ...
   BYP_BOUNCE0 出现在 12 个 mux 族，槽位跨 (4,0) (5,1)
```

⇒ 槽位是 `f(family, source)`，**不是** `f(source)`。任何「按线名/方向排序」的假设都会在这里失败。
这与「每个 mux 实例的引脚排布由它在 tile 中的物理位置决定」一致。

### H3「槽位 = 布线图拓扑序」——未证伪，但先验概率低

H3 需要图距离/tie-break 才能执行，且 H2 已被「同线换槽」反驳，
若 H3 成立也必须解释「同一导线的图距离不变、槽位却变」，因此必须引入 mux 实例位置作为变量。

## 4. 一个 Codex 不知道的正面结果：源集合可离线得到

`law_cells` 的每个 family 的**源集合**，可以直接从 routing 模板离线取到：

```
去掉 VCC_WIRE / GND_WIRE 后，172 个 family 中 166 个的源集合与 law_cells 完全一致
剩余 6 个只差时钟树常量线（LH12 / LVB_L12 / LH0 / GND_WIRE）
唯一差异来源是模板多出常量线，不是结构差异
```

**推论**：攻坚只剩一件事——给定 family 与源，它在 24 个引脚里的**序号**。
源集合、位坐标公式、组结构全都已闭合；这把 Codex 估算的「每个假设 12–18 个 source 状态」
压缩为「每类 mux 只需确定一个引脚顺序表」。

## 5. 与 Codex 方案的分歧（我认为它保守或错的地方）

| 条目 | Codex 说法 | 我的判断 |
|---|---|---|
| 最小实验 4 个构建 | B0–B3 四类构建 | 对 INT_L **不需要**：槽位表已由 `law_cells` 实测（1,536/1,536 已验证）。构建应留给**未测 tile 类型**（BRAM/DSP/IOI），而不是重测 INT |
| 机时 4–8 小时 | 每构建 0.5–1.5 小时 | 实测我们这边是 **75 秒/构建**（xc7vx485t 小设计），差 24–72 倍。它沿用「大设计」的直觉 |
| 「槽位是待测标签，不能从列反称」 | 提醒 | 部分成立，但我们的槽位不是猜的：它是先用位坐标拟合 6×4 网格、再用 1,536/1,536 反证过的 |
| H1 需要「器件线序字段」 | 若 db 无该字段则未验证 | 我已直接证伪：模板按字母序，而且同线换槽——不需要「线序字段」这个概念 |

## 6. 修正后的攻坚路线（我的版本）

1. **立即可做（0 构建）**：把「源集合」的离线来源写进模型（routing 模板 + 常量线白名单），
   让 `verify_all_pip.py` 用模板生成源集合、用 `law_cells` 只提供槽位。
   → 这样模型从「3,634 条查表」变成「模板定集合 + 172 张槽位表」。
2. **要解释的只剩槽位表**：172 族 × 平均 21 个源 ≈ 3,634 个 `(family, source) → slot` 条目。
   对其做统计：是否存在「按 mux 位置（行/列）平移」的规律？这是唯一还没试过的一维。
3. **未测 tile 类型**才需要 Vivado：BRAM/DSP/IOI 各取 1 个 tile、每族 5 个位平面 ≈ 45 构建 ≈ 1 小时。

## 7. 结论

Codex 的方案可以直接用作**验收框架**（表结构、函数签名、通过标准都写得比我细），
但**执行顺序要改**：先做离线可做的（源集合离线化 + 槽位表统计），
把 Vivado 留给真正没数据的 tile 类型。

「复用怎么复用」的答案至此已经完整：
**族内格级共享；共享结构分三类（6×4 网格 / 完全二分 / 组-核心-附加位）；
共享的『谁对谁』由布线图邻接决定，位坐标由几何公式决定。**
