# T81 CRC 语义的文档级证据（UG470 v1.15）

日期：2026-11-11
来源：AMD UG470「7 Series FPGAs Configuration User Guide」v1.15（2022-07-27）日文版，
      本地 `_ug470.pdf`（185 页，4,736,229 B）。
页码为该 PDF 的印刷页码。

## 1. 结论（先给答案）
**CRC 由硬件在配置时强制校验，且默认开启。** 校验不通过 → `INIT_B` 拉低、配置中断、`DONE` 不拉高。
因此对位流做数据位修改后，**必须**同步修正 CRC，否则器件拒绝该位流。我们做的 CRC 增量表是**必需项**，不是装饰。

## 2. 原文证据（p.86，「第 5 章 コンフィギュレーションの詳細 / CRC (手順 7)」）

> コンフィギュレーション データ フレームの読み込み時に、デバイスはコンフィギュレーション データ パケットから
> CRC 値を算出します。… デバイスが算出した CRC 値がビットストリーム内の正しい CRC 値と一致しない場合、
> デバイスは INIT_B を Low 駆動し、コンフィギュレーションを中断します。
>
> CRC チェックはデフォルトでコンフィギュレーション ビットストリームに含まれますが、不要であれば無効にできます
> (『コマンド ライン ツール ユーザー ガイド』(UG628) の「BitGen」参照)。CRC チェックを無効にすると、
> 誤ったコンフィギュレーション データ フレームが読み込まれ、デザインの動作不良やデバイスの損傷を
> 引き起こす可能性があります。
>
> 7 シリーズ デバイスでは 32 ビットの CRC チェックが使用されます。

要点三条：
1. **默认开启**（「デフォルトで…含まれます」）；
2. **失配即中止**（INIT_B 拉低）；
3. **可关闭**，但需在 BitGen 阶段改选项（UG628），且官方明确警告可能造成器件损坏。

## 3. 覆盖范围（p.101–103，表 5-19「XC7K325T のサンプル ビットストリーム」）

表 5-19 逐字标注了 CRC 的覆盖起点与两处 CRC 包：

```
30008001 / 00000007   CMD[4:0]=RCRC（CRC 寄存器リセット）
                      (ビットストリーム CRC のカバレッジがここで開始)
...
3000C001 ...          COR0 / COR1 / IDCODE / MASK / CTL0 / CTL1
30002001 ...          FAR
30004000 / 502BA520   FDRI（类型 2 包，WORD_COUNT = 2860320）
... 2,860,320 个配置数据字 ...
30000001 / C81874CB   CRC レジスタ書き込み（第一个 CRC）
                      (書き込まれた CRC が算出された CRC 値と一致しない場合はエラー)
... NOOP × N, CMD GRESTORE, DGHIGH, START, FAR(03BE0000), MASK, CTL0 ...
30000001 / E3AD7EA5   CRC レジスタ書き込み（第二个 CRC）
                      (書き込まれた CRC が算出された CRC 値と一致しない場合はエラー)
... NOOP × 2, CMD DESYNCH
```

三条与我们实测对得上的事实：
1. **覆盖起点是 RCRC 命令之后**，因此 CRC 覆盖范围包含 COR0/COR1/IDCODE/MASK/CTL0/CTL1/FAR/FDRI 全部，
   不只是 FDRI 数据；
2. **位流里有两个 CRC 包**，与 T79/T80 实测一致（我们此前记录 `_full8_i3.bit` 尾部有两个 `0x30000001`）；
3. 第二个 CRC 值在本器件族上恒为 **`E3AD7EA5`** —— 与我们在 10 个不同设计上测到的常量**完全相同**。
   原因：它只覆盖第一个 CRC 之后的固定序列（NOOP / GRESTORE / DGHIGH / START / FAR / MASK / CTL0 / NOOP / DESYNCH），
   该序列与设计无关。这也解释了为什么它能"十个设计全同"。

## 4. 与其它机制的边界

| 机制 | 文档依据 | 结论 |
|---|---|---|
| 加密位流 | p.86：`BITSTREAM.ENCRYPTION.ENCRYPT = Yes` 时 CRC 失效，改由 HMAC 认证 | 未加密位流才受 CRC 保护 |
| 主模式 CRC 失败 | p.86：主模式（BPI/SPI）下 CRC 错误触发 **fallback reconfiguration** | 与我们无关（我们用 JTAG/SelectMAP） |
| 帧内 word 50 | 本报告不涉及；见 T79/T80（帧级 ECC，另一套机制） | 两套校验相互独立 |
| 同步丢失 | p.86：双时钟等导致同步丢失时，CRC 命令本身不被识别，此时 CRC 被「忽略」，表现为 DONE 低 / INIT_B 高 | CRC 并非万能 |

## 5. 对我们工具链的直接含义

| 结论 | 影响 |
|---|---|
| 硬件必校验且默认开启 | `bitgen.py` / `fasm2bit.py` 改位后**必须**修 CRC，否则位流不可用 |
| 覆盖范围含配置寄存器 | 我们只改 FDRI 数据字 + 两个 CRC 包的值，寄存器区未动 → 增量法（只算数据位贡献）成立 |
| 第二个 CRC 是常量 | 无需重算，原样保留即可（实测 10 个设计全同） |
| 首个 CRC 需重算 | 由 3,200 条位置签名 + 跨帧映射算出（T80，留一法 64/64） |
| 可选关闭 | BitGen 可关，但我们不改 Vivado 生成流程；若将来要"忽略 CRC"，只需改生成参数而非逆向 |

## 6. 仍未验证
- 我们的位流走 **JTAG** 配置（实验室无板卡实测）。UG470 的 CRC 校验描述不分接口，
  属于配置逻辑内部行为，故推断 JTAG 同样校验；**但没有板级实验证据**。
- UG628 里 BitGen 关闭 CRC 的具体选项名未在本次取证中确认。
