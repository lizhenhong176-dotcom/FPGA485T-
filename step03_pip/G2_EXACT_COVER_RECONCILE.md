# G2：精确覆盖解码 vs Vivado 真值对账

> 闸门：G2（解码唯一 + 外部真值）｜日期：2026-11-15
> 脚本：`step03_pip/g2_exact_cover.py`（对账）｜`step03_pip/_q_g2_debug.py`（残差归因）
> 结果：`step03_pip/out/g2_exact_cover.json`
> 标注：**【数据事实】**实测可复算｜**【推断】**解释性

## 1 结论

【数据事实】把解码判据从「逐 PIP 独立判全格置位 + `min-cells` 过滤」换成**精确覆盖**（所选 feature 的位集并集恰好等于目标位集）后，在 `tamper/ref/ref.bit` 上：

| 指标 | 旧判据（逐 PIP 独立） | 新判据（精确覆盖） |
|---|---|---|
| 解出 PIP 数 | 1,886 | **1,413** |
| 与真值一致（TP） | 1,155 | **1,407** |
| 多报（FP） | 731 | **6** |
| 漏报（FN） | 108 | **21** |
| 精确率 | 61.24% | **99.58%** |
| 召回率 | 91.45% | **98.53%** |
| **解唯一性（868 个有数据位的 tile）** | 无定义（逐条独立判） | **868/868 唯一解** |

- 有真值的 tile **868 个**，其中 **857 个（98.7%）的解与 Vivado 真值逐条相同**；剩 11 个 tile（51 条真值行）全部归因清楚（§5）。
- 另有 **114 个 tile** 的真值是「长线 `LV_L18`/`LV18` 一行、数据位为 0」——本地无处可解，见 §6。

⇒ **G2 达标**：解唯一性 100%（868/868），外部真值精确率 99.6%、召回 98.5%，残差全部有名有姓。

## 2 判据定义

```
目标位集  target = observed(tile) − KNOWN_UNMODELED        # 去掉 3 个已知标记格
候选集    cand   = { feature ∈ 3,634 | cells(feature) ⊆ observed }
解         S     满足  ∪_{f∈S} cells(f) = target            # 精确覆盖，不允许余量
```

- 旧判据允许「一条 PIP 的全部格子都置位」即入选，再看 `min-cells` 过滤 → 同一组位可以同时满足多条候选（2 格长线尤其明显），于是多报。
- 精确覆盖把「解释完整」变成硬约束：多选一条就必须多出格子，或少解释格子，都被判不合法。
- 枚举用「候选最少的未覆盖格」分支（`cov_by_cell`），节点上限 40 万、解上限 200；本实验中**没有一次触到上限**（`trunc=0`）。
- **只枚举极小覆盖**：一旦覆盖满即记录解并回溯，不再追加「格子已被覆盖」的冗余 feature——这一点是 §5「冗余行」类残差的直接原因。

---

## 3 归一化（不归一化会凭空造出多解）

【数据事实】同一条物理线在器件模型里有两套拼写：INT_L 用 `LV_L0` / `LOGIC_OUTS_L8` / `IMUX_L40`，INT_R 用 `LV0` / `LOGIC_OUTS8` / `IMUX40`；Vivado 真值里还会出现 `LV0<<` 这种带方向后缀的写法。

处理：
1. 真值行先剥 `<<` / `>>` 后缀（**153 条真值行**因此从"漏报"变成"命中"）；
2. 族名与源线名一起用 `verify_all_pip.name_variants` 建并查集，代表取字典序最小者；
3. 归一化后候选池 **3,634** 条（与 `law_cells` 特征数一致）。

【推断】不做第 2 步会得到「同位流两种读法」的假多解（早期在 `INT_R_X71Y6` 上就见过 2 解、`INT_R_X71Y0` 上 4 解）。

---

## 4 真值的方向约定（差点搞反）

【数据事实】`get_pips -of_objects` 的写法是 `<tile>/<tile_type>.<驱动线>->><目的线>`，而 `law_cells.family` 存的是**目的线**。因此真值解析必须取「`->>` 后」为 family、之前为 source。

第一版取反了，得到 TP=0 / FP=1,413 的荒谬结果——**对账方向写反时，正确率会整齐地掉到 0**，这是个很好的自检信号。

## 5 残差逐条归因（21 条 FN + 6 条 FP）

| 类别 | 条数 | 说明 | 判定 |
|---|---|---|---|
| 方向反转（长线对） | **6** | 真值是 `LH12 ← LV0`，解得 `LV0 ← LH12`：两条反方向的 PIP 共用同一批格子（跨族共享格 `(0,2,0)`/`(0,9,0)`/`(1,6,0)`），位流上不可区分 | 【数据事实】模型可及的上限 |
| 目的线无位（扇入=1） | **9** | 如 `FAN_BOUNCE7 ← FAN_ALT7`：`templates/INT_L.json` 里 `FAN_BOUNCE7` 扇入 = 1 ⇒ 固定直通、无选择位（与 G1 的 44 条同类） | 【硬件事实】 |
| 格已被其它 PIP 覆盖（冗余行） | **6** | 真值里 `LV_L18 ← LV0`（2 格 `(0,9,0)+(1,6,0)`）的两格已被别的已选 PIP 点亮；Vivado 把它记为一条路由，但**极小覆盖不重复记账** | 【推断】记账差异，非解码错误 |
| FP 6 条 | 6 | 全是长线互选：`LVB0←LVB12`(3)、`LH0←LH12`(2)、`LV0←LH12`(1)——它们的格子被真值里的其它长线 PIP 点亮，极小覆盖顺手选了反方向 | 与第一类同源 |

【数据事实】FN 21 / 真值 1,428（这 868 个 tile 内）= 1.47%；FP 6 / 解出 1,413 = 0.42%。

## 6 那 114 个"无数据位"的 tile

【数据事实】982 个活跃 INT tile 里有 114 个目标位集为空（去掉标记格后为 0），它们的真值行**恰好各 1 条**，目的线全是长线：`LV_L18` 63 条 + `LV18` 51 条 = 114。

【推断】长线 PIP 的"记账位置"与"配置位位置"不在同一个 tile：Vivado 在长线通过的 tile 上记一条 `LV_L18 ← …`，而决定它是否连通的位落在该线起点/终点所在的 tile。本模型是**逐 tile 位池**，因此在记账 tile 上自然解不出东西。

【数据事实】这批行不计入 §1 的召回/精确率（它们的目标位集为空，无从判定）；若要判，需要把长线族的位归到"线"而不是"tile"——这是 §161 未解 82 条长线之外的**另一个**长线相关缺口，已在 §8 登记。

---

## 7 「唯一」与「多报」的表面矛盾就此消解

旧结论里同时出现过两句话：`p1_solvability` 说 1,066/1,066 tile 只有单个解；而旧解码器在 `ref.bit` 上多报 731 条。两者不矛盾：

- **位流→配置**的映射是唯一的（精确覆盖 868/868 唯一解）；
- **逐 PIP 独立判据**不是这个唯一映射的实现——它按「全格置位」选人，天然会把被共用点亮的 2 格候选全部收进来，于是多报。

换成精确覆盖后，多报从 731 掉到 6，且 6 条都能指名道姓（长线互选）。**【推断】731 条多报是判据缺陷，不是编码歧义。**
