# INT tile 的 PIP 复用规律 —— 实验讲解稿

> 面向：导师 / 学长 / 答辩听众
> 讲三件事：为什么这么切入、最后拿到了什么、中间踩了哪些坑（以及没发现会得出什么错结论）
> 标注约定：**【硬件事实】**硅片/工具链事实 ｜**【数据事实】**我跑出来的可复算数字 ｜**【推断】**解释性判断
> 复算入口全部在 `step03_pip/`，索引见 §11

---

## 1. 一句话总纲

**INT tile 里 3,634 条 PIP 连接只占 1,598 个配置位，这套"多对一"的位复用不是随机的：97.7%（3,552/3,634）可以由"族名 + 源名"按规则生成，逐位 0 差异；剩下 2.3%（82 条）确认是表数据，且已证明它们与其余族是同一编码形式的稀疏实例。**

---

## 2. 实验对象与约束（为什么从这个切入点开始）

**对象**：XC7VX485T 的 `INT_L` / `INT_R` tile（各 26,550 个实例）。一个 INT tile = 600 根 wire、3,737 条 PIP、216 个目的 wire。

**约束（决定了方法）**：

| 约束 | 后果 |
|---|---|
| 没有 V7 的公开位库（prjxray 的 `segbits_<T>.db` 在 `manifest.json` 里标 `missing`） | 不能"读表"，只能自己造真值 |
| 没有比特流格式文档、没有布线代码 | 唯一可信的真值支点是 **Vivado 自己的一致性**（同一设计两次构建逐位相同；换一个属性只动该动的位） |
| 需要的是"编码规律"，不是"位表" | 判据必须是**可反驳的公式**：用公式重建全部置位，逐位比对 0 差异；否则只能算抄表 |

所以整条路线只有一个骨架：**受控差分 → 位池定位 → 列重统计 → 结构判定 → 两轴归属 → 生成器重建 → 反证 → 迁移**。

---

## 3. 实验思路：8 步链（每步都写"排除了什么"）

### 3.1 第一步：先造一个"有真值"的位流
- **为什么**：没有真值就没有判据。先用 24 级 LUT6 链 + 显式 `LOC/BEL` 造 `ref.bit`，Vivado 的 `get_pips -of_objects` 给出 1,812 条布线（其中 INT 侧 1,263 条）。
- **排除了什么**：排除了"用现成开源位流当输入"这条路——V7 位流在公开语料里没有配套布线真值。
- **当时得到**：一个 20,273,538 B、982 个 active INT tile 的被测对象。

### 3.2 第二步：把"位流里的位"变成"tile 内坐标"
- **为什么**：位流是帧序列，必须先解 `frame = far_bands[(band,col)].start_frame + frame_off`、`word = 2*(Y%50)+parity`（≥50 再 +1 跳过 word 50）。
- **排除了什么**：排除了"帧内全 101 字都是数据"的假设——word 50 是 ECC，实测每对差分里都有 4–20 个 word 50 的格随数据变化。
- **当时得到**：`(tile, frame_off, parity, word, bit)` 五元组，覆盖 54.49% 配置位。

### 3.3 第三步：找"槽位不变量"（这一步是整个结论的地基）
- **为什么**：如果同一族的不同源共用一组位，那么"哪位属于哪个源"必须有结构；先验证"是否存在不变量"比先猜规律安全。
- **怎么排**：对每个 `(tile, bit, parity)` 槽位，读 6 个行帧与 4 个列帧：行集合必须 ≤1 个元素、有行则码字必须 ∈ `{1,2,7,11}`、有码则必须有行。
- **排除了什么**：排除了"位分配是随机的"。
- **当时得到**：**231,656 个槽位、0 违例**（73,152 + 97,024 + 60,480）。

### 3.4 第四步：6×4 网格
- **为什么**：24 源族若是一张网格，就能把"每源的位集合"压成"行号 + 列码"。
- **怎么排**：按列重切两轴——列重 4 的 6 个格是行选择位，列重 18/18/6/6 的 4 个格是列码位。
- **排除了什么**：排除了"行号靠名字顺序""列码任意"两种解释（见 §7 的证伪）。
- **当时得到**：**64/64 族帧集合恰为 `16..25`、行格 6 个列重均 4、384 个行格全部 `frame = 16+r`、16 种配置每种 4 族**。

### 3.5 第五步：BEG 族（20 源）是完全二分
- **为什么**：BEG 的源数 20 = 5×4，与 mux 的 24 = 6×4 同构，若不验证"是否也有网格"，推广就是猜。
- **怎么排**：把源当边、两个 cell 当端点做 2-着色，**不看族名、不看帧号**。
- **排除了什么**：排除了"BEG 是 8×7 稀疏表"——那是把 `pip_defs` 顺序当边序造成的假象。
- **当时得到**：**96/96 完全二分（K(5,4) 64 族 + K(4,5) 32 族）**；P 轴 = 方向令牌 96/96，Q 轴 = 几何类别 64/96 纯净，剩 32 个变体族用 640/640 的补充规则闭合。

### 3.6 第六步：复合族（16 源 6 族）
- **为什么**：这 6 族（`CLK_L0/L1`、`CTRL_L0/L1`、`GFAN0/1`）每源的格数不是 2 也不是 4，硬套网格必错。
- **怎么排**：用"core（3 格）+ drops（2 源各去 1 格）+ extras（2 源各加 1 格）"的组模型，**先过滤 sense=1**。
- **排除了什么**：排除了"这 6 族需要并入恒定 cell 才能对齐"的说法——那是混算 sense=0 的产物。
- **当时得到**：**96/96 源精确命中、不符 0**。

### 3.7 第七步：生成器重建（这一步才算"拿到规律"）
- **为什么**：模型再漂亮，不能用名字重建就还是表。
- **怎么排**：`gen_mux.py`（cell 级）与 `gen_slots.py`（槽位级）只吃族名与源名，输出每个源的位集合，与 `law_cells` 逐位比对。
- **当时得到**：**mux 64/64、BEG 96/96、复合 96/96 → 3,552/3,634 = 97.7%，0 差异**。

### 3.8 第八步：反证与迁移
- **反证**：真值对账 1,155/1,263 = 91.45%；线长律 12,565 tile / 64,686 位 / 表外 0；改 `BUFGCTRL.SEL` 重生成与 Vivado 独立产物 50,176 帧全等。
- **迁移**：HCLK_CMT 11/11 源"1 组槽位 + 2–4 码字"同形；时钟区 6 对受控差分每对恰 2 数据格、跨 `minor26/27`、位号差 8。

## 6. 中间遇到的问题（重点：每条都要写"没发现会得出什么错结论"）

### 6.1 数据获取类

**P1｜Vivado 在中文路径下静默崩溃**
- 症状：日志停在 `done synthesizing module 'top'`，stderr `TclStackFree: incorrect freePtr. Call out of sequence?`，`EXIT=3`。
- 根因：Vivado 2017.2 在非 ASCII 工作目录下的已知缺陷，与脚本无关。
- 发现：把日志与退出码逐个比对（同脚本在 `C:\Temp` 下成功）。
- 修法：源码拷到纯 ASCII 目录构建，产物再拷回工作区。
- **错误结论的样子**：会报"我们的 tcl 写错了 / 环境坏了"，然后去改脚本，浪费一整天且永远修不好。

**P2｜远端 locale 崩溃**
- 症状：`rc=134`，`locale::facet::_S_create_c_locale name not valid`，进程 core dump。
- 根因：远端 `LANG` 是非 UTF-8 值，Vivado 的 C++ 本地化层直接 abort。
- 发现：构建脚本统一 `set -x`，看到 abort 前的 tcl 与其它成功批次不同。
- 修法：`LANG=C.UTF-8` + `unset LANGUAGE`，写进固定脚本。
- **错误结论的样子**：会报"非 ASCII 路径不能让 Vivado 跑"，而实际非 ASCII 设计名在 UTF-8 locale 下是能跑的。

**P3｜漏 `LOCK_PINS` 导致"形状随设计变"**
- 症状：同一逻辑、三次构建得到三张不同的位表。
- 根因：未锁引脚时路由器自由重排 I/O，位形状跟着变。
- 发现：把三次的 `.pips` 做集合差，发现源线完全不同。
- 修法：`LOCK_PINS` 固定，且管脚名用 `get_bel_pins` 实测而非猜。
- **错误结论的样子**：会报"编码不唯一、同一族有 3 种形状"，直接把结论推翻。

**P4｜`DONT_TOUCH` 不阻止常量传播**
- 症状：某位平面整体反相，与预期完全相反。
- 根因：优化器把常量逻辑简化，位平面被整片翻转。
- 发现：对比"同逻辑不同 INIT"的两次构建，只有该平面反相。
- 修法：改用"逻辑等价但结构不同"的差分对照，不用纯常量。
- **错误结论的样子**：会报"ZINI 极性反转"这类假极性规律，后续所有极性判断都会错。

### 6.2 判读类

**P5｜把 XOR 差分当 PURE 差分**
- 症状：位形状随 CLB 位置变化。
- 根因：两设计都置位时，XOR 会把"共有的置位"抵消掉，表就变成"差异表"。
- 发现：同一族在两个 CLB 位置得到不相交的位集合。
- 修法：先声明差分语义（PURE / XOR / FAM），XOR 只用于"两次都有"的比较。
- **错误结论的样子**：会报"同一族在不同 tile 用不同位"，即"族不唯一"，整套复用模型作废。

**P6｜漏 `parity` 把两族看成一批位**
- 症状：`IMUX_L0` 与 `IMUX_L4` 的位集合完全一样。
- 根因：`parity` 是 word 的第二维，漏掉它会把 `word = 2*(Y%50)+0` 与 `+1` 混成同一格。
- 发现：按 `(frame_off, bit)` 分组时两族撞车，加上 parity 后分离。
- 修法：`law_cells` 的 cell 定义必须是 `(frame_off, parity, bit)` 三元组。
- **错误结论的样子**：会报"两族共用同一批位 → 复用度虚高一倍"。

**P7｜把 word 50（ECC）当数据位**
- 症状：每对差分多出 4–20 个"数据格"，且这些格随任意数据变化。
- 根因：word 50 是 ECC 字，数据一改就重算。
- 发现：把这些格单独统计，发现它们**必随数据变化**、且数量与数据变化量相关。
- 修法：`word_of()` 里 `≥50 则 +1` 跳过，且差分统计时单列计数。
- **错误结论的样子**：会报"mux 族容量比实际大 1/3"，并把 ECC 当选择位写进生成器。

### 6.3 统计类

**P8｜`sense=0` 混算（最严重的一次）**
- 症状：算出"每源恒 5 格、每 cell 被 24 个源共用、102/172 唯一、70 族 4:1 合并"。
- 根因：`law_cells` 同时存 `sense=1`（必须置 1，8,900 行）与 `sense=0`（必须为 0，3,264 行），混在一起求并集就变成"每源 5 格"。
- 发现：按 sense 分列后 `2,818×2 + 816×4 = 8,900` 精确闭合，混算则对不上。
- 修法：所有比对先 `sense=1` 过滤；这条写进 `T35` §6 与 STATUS。
- **错误结论的样子**：会发一篇"172 族里只有 102 个唯一组合、70 族 4:1 合并"的论文——**这条新颖性结论是假的**。

**P9｜INT_R 命名不对称造成 63.6% 假缺口**
- 症状：`verify_all_pip.py --tile-type INT_R` 报覆盖 2,312/3,634 = 63.6%、未覆盖 1,274。
- 根因：器件左右侧线名不同（`IMUX_L40` vs `IMUX40`、`CLK_L0` vs `CLK0`、`GCLK_L_B0` vs `GCLK_B0_EAST`），字面比对自然对不上。
- 发现：把"未覆盖"的名字列出来，发现全是左/右命名的变体。
- 修法：`name_variants()` 做归一化，`--normalize` 同时作用于族名与源线名。
- **错误结论的样子**：会报"V7 右半器件位库缺失 1,274 条"，进而以为只有半侧能做。

**P10｜检测器未减基线 → 幽灵 mux 假 100% 检出**
- 症状：篡改检测实验里"幽灵 mux"报 300/300 = 100% 检出。
- 根因：判据写成 `if unexplained or violations`，没减掉干净位流本身的 240 个白名单标记位；120 个 tile 天生带这些位，全被算成"检出"。
- 发现：先跑干净基线（240 位 / 120 tile），与注入后的签名做差，检出降到 0。
- 修法：`_tile_signature()` + `_detect(world, M, ti, sig0)` 只比增量。
- **错误结论的样子**：会报"2 bit 篡改 100% 可检出"——**这条会把整个"2 bit 可藏身"的结论反过来**。

**P11｜`code_of` 位序写反**
- 症状：干净位流上出现 64 个槽位违例。
- 根因：`sum(v << (3-i))` 把帧 25-i 映射到码位 3-i，正确是 `sum(v << i)`。
- 发现：违例数恰好等于族数 64，可疑；改成 `<< i` 后归零。
- **错误结论的样子**：会报"不变量在真实位流上不成立，整套模型作废"。

**P12｜换源实验的复原污染共享格**
- 症状：换源检出 29%（有共享 49.6% / 无共享 15.9%），与理论预期差太远。
- 根因：`set_cells(diff_on, 0)` 无条件把共享格写 0，把别的 PIP 也写坏了，误差逐样本累积。
- 发现：同一 seed 重跑两次结果不同（不该不同）。
- 修法：逐格保存原值再恢复。
- **错误结论的样子**：会报"换源有 29% 可检出"，而真实是 6.0%；论文里的"可检出性"会虚高 5 倍。

### 6.4 工具能力类（"我算错了" vs "工具不给"要分开）

**P13｜`pip_defs` 的 `delayIndex` 在 INT 全 0**
- 症状：想用模板里的延迟字段排序线源，发现 3,737 条全是 0。
- 根因：RapidWright 对该字段在 INT tile 不填。
- **错误结论的样子**：会报"线源顺序 = 延迟序"，其实是空表排序，毫无意义。

**P14｜没有版图级 API（行轴只能写推断）**
- 症状：`Site.getSitePIPs()` 对 SLICEL 返回 138 条，全是 `D6LUT.A1->>O6` 这类 LUT 输出选择；`Tile` API 没有 tile 内部行列坐标；Vivado `link_design` 批处理探针挂死 >10 分钟。
- 根因：两套工具都只暴露"逻辑连接"，不暴露开关矩阵物理位置。
- 修法：放弃"从工具证明版图"，改写成【推断】，并把"列轴有厂商元数据（每组恒 2 DOUBLE + 2 SINGLE）、行轴无"如实写进结论。
- **错误结论的样子**：会报"6 行 = 物理上 6 行"，这是没有证据的断言，答辩一问就塌。

**P15｜`BUFGCTRL_X0Y32` 非法站点**
- 症状：`ERROR: [Common 17-69] 'BUFGCTRL_X0Y32' is not a valid site name`。
- 根因：合法站点只到 `X0Y31`。
- **错误结论的样子**：会报"GCLK 有 62 个源"，而实际 GCLK 源是 32 个。

### 6.5 文档与脚本类

**P16｜`open(w).write(格式化字符串)` 把 STATUS 清成 0 字节**
- 症状：`STATUS.md` 变成 0 字节。
- 根因：Python 先截断文件再求值参数，参数里 `.format()` 撞上正文花括号（`{EE,NE,WW,SW}`）抛 `KeyError`，文件已空。
- 修法：先算成字符串再单次写；占位符改 `__N__`；`newline=""` 保留 CRLF；事后用 `git checkout -- STATUS.md` 恢复。
- **错误结论的样子**：不算错结论，但会**丢整份项目现状**（4,000 行）。

**P17｜PowerShell 文本管道毁掉中文源文件**
- 症状：`SyntaxError: unterminated triple-quoted string`。
- 根因：PS 5.1 的 `Get-Content -Raw` 按 GBK 解码 UTF-8，中文注释变乱码；某次 `STATUS.md` 因此整文件 mojibake，部分字符变 `?` 不可逆。
- 修法：一律 Python `io.open(encoding='utf-8')` 读写；改文档只用定点 edit。
- **错误结论的样子**：同上——文档级损失，且不可逆。

## 7. 撤回 / 不再主张的结论
