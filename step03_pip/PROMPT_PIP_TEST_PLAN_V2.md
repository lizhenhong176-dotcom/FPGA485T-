## 用户处境
用户是这个 FPGA 比特流逆向项目的主人，长期围绕「PIP 复用规律」这条主线推进，但对测试组织方式缺乏清晰图像：不清楚自己跑过哪些测试、哪些仍在运行、哪些结论由哪些测试支撑。现在需要一份可一眼看懂的「测试方案 + 待跑清单 + 进度」。

## 交付物结构（必须逐节出现，不得合并或省略）
1. 测试分层总览：按证据强度从强到弱分为 5–6 层，每层给出层名、该层要回答的核心问题、该层与其他层的依赖关系，并为每层给出一个**反例设计**（即该层测试若失效时会表现成什么样），反例必须具体到可观察的错误现象，不得只写「会出错」。至少覆盖以下六类，可调整命名但不得删层：
   - 回归层：仓库自带测试、口径校验
   - 单点差分层：受控差分位流，逐位比对
   - 全族对账层：生成器 vs 位库，逐 feature 逐 cell 比 0 差异
   - 外部真值层：第三方工具/模板/几何律给出的独立判据
   - 变异与对抗层：注入篡改，量检出率与误报
   - 迁移层：跨 tile 类型、跨器件、跨设计规模
2. 分层测试表：每层一张表，列固定为：测试名 / 判据（可量化的分子分母） / 输入 / 脚本路径 / 输出产物 / 当前状态 / 失败意味着什么。不得增删列，不得把多列合并成一列。每层还需在该表之外单列一条「反例设计」，说明该层测试失效时的可观察表现。
3. 运行现状节：单设一节，明确回答「现在有没有测试在跑、最近跑完的是什么、什么时候跑的」，并给出最近一次跑完产物的时间戳；为每条测试标注三种状态之一：**已验证**、**已跑过**、**从未跑过**，其中「已验证」必须满足判据分子/分母达标，「已跑过」仅表示执行过但不等于通过，二者不得混同。
4. 进度节：全部用分子/分母表达，禁止使用「基本完成」「大致可以」「接近完成」等模糊说法；每一处分母必须明确标注来源（来自哪份清单、哪次实测输出或哪张表），不得出现无来源分母。
5. 方案边界节：标题为「这套方案证明不了什么」，列至少 5 条具体边界，每条说明该边界对应的测试缺口。
6. 下一步节：标题为「下一步只做三件事」，按性价比从高到低排序，每件事给出预期证据增益与所需输入。

## 硬性纪律（逐条执行，不得放宽）
- 三色标注：每条结论前缀必须是【硬件事实】/【数据事实】/【推断】之一，不得混写，不得省略前缀。
- 数字只能来自给定清单或实测输出；清单里没有的写「未测」，不许估算、不许外推。
- 禁止使用「首次」「唯一」「完整」「彻底」这类不可反驳的形容词。
- 禁止把「脚本多、文件多」当作进度证据，进度只能由分子/分母与产物时间戳支撑。
- 每条测试必须给出复算命令；给不出就明写「无可复算入口」并说明原因。
- 严格区分「已验证」「已跑过」「从未跑过」三种状态：「跑过一遍没报错」只能记为「已跑过」，不得等同于「已验证」；只有判据的分子/分母达标才可记为「已验证」。
- 表格中每一格的判据必须写成可计算的分子/分母形式，不得只写「通过/不通过」。

## 输出格式要求
- 先输出分层总览（含每层反例设计），再逐层输出表格，最后依次输出运行现状、进度、方案边界、下一步四节。
- 全文使用中文，表格使用 Markdown 表格。
- 若某字段信息缺失，填「未测」或「无可复算入口」，不得留空、不得编造。
