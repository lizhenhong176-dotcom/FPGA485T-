# 抽样回归失败点定位（S_8_161）

## 观察

`S_8_161` 的路由链（22 条 PIP）大部分是**长线/六方向线**家族：

```
NN6BEG0/LOGIC_OUTS_L12   LV_L0/NN6END0   LV_L18/LV_L0 ×4
NW6BEG1/LV_L9   NN6BEG1/NW6END1   NN6BEG1/NN6END1 ×8
NE6BEG1/NN6END1  NL1BEG0/NE6END1  NR1BEG0/NL1END0  IMUX_L8/NR1END0
```

观测到 21 帧、42 位，只有 4 位命中预测（都在帧 31680 的 LV_L0/NN6END0）。

## 关键数据（观测位 → CSV 里的块）

| 观测帧 | CSV row | 块地址 | 块列 |
|---|---|---|---|
| 142 / 144 / 147 | 1 | `0x200` | 4 |
| 5389 / 5392 | 2 | `0x20200` | 4? |
| 5458–5475 | 2 | `0x20300` | 6 |
| 26434 / 26435 | 6 | — | — |
| 31680–31685 | 7 | `0x420300` | 6 |

## 结论（推翻上一轮的“band 映射错”）

1. **band 公式没错**：同一链里 `INT_L_X6Y10` 的 `NN6BEG0` 预测到 31683 附近，实测确实在 31680–31685，方向正确。
2. 真正的问题是：**长线家族（LV/LH/NN6/NW6/NE6…）的配置位不在本 tile 的 CLB 列块里**。
   - LV 位的落点在 **块列 4 / 块行 1**（帧 142–147），而 tile 是 X6 → 差了 2 列、6 个行带；
   - 另有部分落在块行 2（帧 5389–5475）。
3. 表里这些家族确实有（`pip_law._ALL` 共 228 个 sink 名，含 `LV_L0`、`LV_L18`、`NN6BEG1`），
   但表里的 `(offset, bit)` 是在 **Y11/Y21 的 CLB 列块**上测的，长线家族的块归属与之不同 —— 所以按
   `block_start(col) + offset` 预测必然打偏。

## 修正后的模型

```
地址 = f(家族, 块归属规则) + 形状项
```

- **CLB 列块规则**（IMUX / *_BEGn / FAN / VCC 等）：`block = (row 由 Y 决定, col 由 X 决定)`，offset ∈ 16..25 —— 已由 150/150、792/792 验证。
- **长线规则**（LV/LH/NNn/NWn/NEn…）：需要单独确定 block 的列/行归属。目前只确认了两点：
  - LV 位出现在**块列 4、块行 1**；
  - 长线可能有**多份副本**（同一设计里同一 PIP 同时在 31680 与 142 出现）。

## 下一步（最小实验）

1. 做一个**只含一条长线**的对照：net 从 `SLICE_X6Y10` 出发，只经 `NN6BEG1/NN6END1` 走到相邻 INT tile，不碰 LV/IMUX；
2. 逐 PIP 删除（不是全删），得到每个长线家族的**单独位集**；
3. 用这些位集反解长线家族的 block 列/行规则。

在此之前，`pip_law` 只对「CLB 列族」有效，`PIP_LAW.md` 需要写明这个适用范围。

## 单 PIP 删除实验（one/，22 个位流）（补充 2026-10-26）

对 `S_8_161` 的 22 条 PIP 逐条删除（`del_one.py`，保留其余），各自与完整 `ref` 差分：

- 22 个位流全部成功（`/opt/lzh/step03/one/d*.bit`），差分结果 `one_obs.json`。
- 观测到的位仍集中在同样几个块：**帧 142/144/147（块列 4、行 1）、5389–5475（行 2）、26434–26440（行 6）、31680–31685（行 7）**。
- 帧 142 里出现 `word = 14, 26, 38, 51, 63, 75, 87, 99`（步长约 12），bit 恒 22 —— 这是**长线轨道**的排布：一条长线占一个 word，同一帧容纳多条。
- 逐条删除的位集**高度重叠**（`unique=0/22`），说明删除任意一条 PIP 都可能让整条长线链失效，这些位不是“一条 PIP 一位”的干净对应，需要改用“单段长线”对照才能拆开。

### 由此确定的下一步

1. 做“单段长线”设计（只经一条 LV/NN6 段，不接 IMUX），得到该段的**独占位集**；
2. 用独占位集确定长线家族的 block 归属与 word 间距（当前看是 `word = 14 + 12k`，帧 142/144/147）；
3. 把这些规则并进 `PIP_LAW.md` 的“长线族”一节。

## 多 PIP 叠加的量化归因（补充 2026-10-27，远端从 `.bit` 重算）

把 24 个 `sweep1/S_*` 设计（每个含 606 条 PIP、其中 558 条 INT）在远端
`/opt/lzh/verify` 用 `v_bits.py sweep` 直接从 `.bit` 重算，与 `pip_law.predict_family`
的**逐 PIP 并集**对照。结果（`remote_out/out_sweep.json`）：

| 判定 | 设计数 | 含义 |
|---|---|---|
| EXACT | 7 | 观测位集 == 预测并集，逐格相等 |
| MIX | 17 | 观测数 == 预测数，但集合不同（**重定位**，非计数错） |
| EXTRA / SUB | 0 / 0 | 没有多出、也没有缺失总数 |

全局位级统计（`_sweep_diag2.py`）：

* `in_pred1 = 892`（观测位落在某个 PIP 的 `sense=1` 预测格上）
* `in_pred0_only = 0`（**没有**任何观测位只落在 `sense=0` 格上 → 叠加不会产生假阳）
* `truly_extra = 258`、`pred1_missing = 258`（**完美平衡** → 是重定位，不是数量错）

### 失配 100% 归因于跨块长线 sink

`pred1_missing` 按 owner 家族分类：

| owner（sink ← src） | 缺格数 | 类别 |
|---|---|---|
| `LV_L18 ← LV_L0` | 214 | 长线 |
| `LV18 ← LV0`（INT_R） | 22 | 长线 |
| `LH0 ← LV_L0` | 20 | 长线 |
| `LH0 ← LV0`（INT_R） | 2 | 长线 |
| **合计** | **258** | **长线 258 / CLB 列家族 0** |

`truly_extra` 落在块行 `frame//5246 ∈ {0,1,2,3,5,6}`（52/48/20/12/82/44）——
即长线位搬到了**它们自己的块**里，不在 CLB 列块。

**关键细化（比上一轮更精确）**：并非所有长线 PIP 都失配。`in_pred1` 里
`LH12←LH0`(28)、`LV_L0←NN6END0`(22)、`LH12←LV_L18`(14) 这些长线 PIP **命中**了预测——
它们的端点没有跨块。只有 **`LV_L18` / `LH0` 这类跨块的长线 sink**（18 格跨度的纵向线）
其 segbits `frame_off` 不走 CLB 列的 `block_start`，因而重定位。

### 由此得到的结论（可直接写进规则）

1. **多 PIP 叠加对所有 CLB 列家族是干净的逐 PIP 并集**：892/892 格正确，0 假阳，
   0 个“置位却预测 sense=0”。这补上了 §6.1 里“多 PIP 线性叠加未系统验证”的缺口
   ——对 CLB 列家族成立。
2. **唯一失配是跨块长线 sink（`LV_L18`/`LH0`）**，258 格全部可归因，落点分散在
   多个块行。`pip_law` 的适用范围因此被精确界定为：**CLB 列家族 + 不跨块的长线 PIP**；
   跨块长线 sink 需要单独的 block 归属规则（仍未解，见上文“下一步”）。
3. `FAN_BOUNCE7 ← FAN_ALT7`（2 次）在形状表里**根本没有条目**（`no_shape`），
   是 prjxray segbits 的覆盖缺口，与长线问题无关。
