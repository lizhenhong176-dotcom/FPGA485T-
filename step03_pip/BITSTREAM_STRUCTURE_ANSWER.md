# 比特流配置结构 × tile 帧空间分配（回答版）

> 对应提示词：`PROMPT_BITSTREAM_STRUCTURE_V2.md`。所有数字标来源与口径：
> 【UG470】文档 · 【prjxray】开源实测 · 【本项目实测】本仓库脚本 · 【推断】 · 【未测】
> 实测样本：`E:\v7work\_s8v0.bit`（20,273,538 B，Vivado 2017.2 生成，top 设计 = 1×LUT6 + 1×FDRE + 1×LUT2）。

---

## ① 一句话总览

比特流 = **ASCII 头 + 同步字 + 一小组寄存器写（约 25 个包）+ 一次连续的 `FDRI` 突发（正好 50,176×101 = 5,067,776 个字，覆盖整片配置空间）+ 尾部 CRC/启动命令**；整片配置在帧空间里是**一维连续编号**的，因此"tile 分配帧空间"= 一张**块基址表**（CLB 36 帧 / INT 28 帧 / 接口列 28 帧），而块基址由 `(grid_col, clock_region)` 决定。【本项目实测 + 推断】

## ④ 帧层与 FAR

### 4.1 已定事实

- 帧数 **50,176**、每帧 **101 字**、每字 **32 位** → 5,067,776 字 / 20,271,104 B（数据区）【本项目实测】
- 文件 20,273,538 B − 150 B 头 − 4 B 同步 − 数据区 = **尾部/命令开销 2,280 B**【本项目实测】

### 4.2 FAR 位域：假设 + 验证法（不给定论）

两次 FAR 写值实测：`0x00000000`（起点）与 `0x03BE0000`（启动前）。
把 0x03BE0000 拆成 27 位：`000 0011 1011 1110 0000 0000 0000 0000`，可见**低位 16 位全 0**，高段 `0x3BE`。

假设 A（列优先，`FAR = {block:?, row:?, col:6, minor:?}`）：0x3BE0000 落在 die 右上角一列，与"启动前最后一次 FAR 指向 IO/GTX 侧列块"自洽。
假设 B（线性帧号）：则不成立，因为 0x3BE0000 = 62,914,560 ≫ 50,176。【推断】

**验证法（可执行，不需板卡）**：
1. 用 Vivado 生成两个只差一个 tile 位置的 bitstream（同一设计，把一 LUT 从 X8Y11 移到 X47Y51），diff 出数据区偏移 → 换算成帧号；
2. 同时导出两版的 `get_property FAR` 不可行（Vivado 不暴露），改用 `write_bitstream -verbose` 日志里无 FAR；故改为：**用本项目块基址表反推**——已知帧号 N ↔ tile 的映射来自 763 个 CLB 块的实测，只要找到"帧号 N 的 data word 与某 tile 的已知字段位一致"即可标定；
3. 判定标准：若两版 bitstream 的差异帧号差 = 块基址表预测差，则块表与 FAR 语义一致；反之块表有错。

### 4.3 5,180 与 5,246 的关系（实测）

- **5,180** = 一个 clock region 带内所有块所占帧数（含 36 帧 CLB 块、28 帧接口块）
- **5,246** = 相邻带**起始**帧之差 = 5,180 + **66**
- 66 = 带间填充（含 2 个 overhead 帧 + 对齐）
- 7 × 5,180 = 36,260；fabric 止于 36,688；**50,176 − 36,688 = 13,488 帧属 IO/GTX/CFG 侧**

**能否推出 50,176 的整齐公式？→ 不能。** 412（gx 列）× 365（gy 行）= 150,380（tile 数），与 50,176 无整数关系；50,176 = 7 带配置块 + 13,488 帧侧区 + 带间填充，只能逐块累加。任何"列数×行数=帧数"的写法都是错的。【本项目实测】

## ⑤ 帧内字段布局

### 5.1 块模型

| 块类型 | 总帧 | 数据帧 | overhead | 位池容量 | 实测依据 |
|---|---|---|---|---|---|
| CLB tile | **36** | 34 | 2 | 34×2×32 = 2,176 位 | 字段偏移 0..35 |
| INT tile | **28** | 26 | 2 | 26×2×32 = **1,664 位** | 与 1,598 覆盖 + 66 未覆盖吻合 |
| 接口/BRAM 列 | **28** | 26 | 2 | 1,664 位 | S13 ghost 事件 |

### 5.2 CLB 块内布局（实测，偏移相对块基址）

```
帧偏移 0..15   未解字段（可能与 slice PIP / 控制相关）      【未测】
帧偏移 16..25  IMUX 选择位：10 帧 × 2 字 × 32 = 640 位       【本项目实测：全满 640/640】
帧偏移 26..29  未解字段                                     【未测】
帧偏移 30..31  FF 相关（AFFMUX/ZRST/ZINI/FF 类型标记）       【本项目实测】
帧偏移 32..35  LUT INIT：4 帧 × 2 字 × 32 = 256 位 = 4×64    【本项目实测，A/B/C/D 四 LUT 共用该 4 帧不同位】
帧 34/35 之后  2 个 overhead 帧（对本设计全 0）              【本项目实测】
```

字规则：`word = 2×(Y%50) + (1 if (Y%50)≥25 else 0) + parity`，`parity = 原始位号 // 32`。【本项目实测】

### 5.3 一处必须纠正的旧说法：word 50

早期文档写"word 50 = ECC（每帧都有）"。本次全帧统计：**50,176 帧里 word 50 非零的只有 157 帧**（值如 0x8B4、0xAC0、0x8019B7，最大 24 位）。若 word 50 是每帧 ECC，不可能 99.7% 为零。

修正表述：
- 【本项目实测】word 50 在**少数特定帧**非零，且这些帧聚集在特定区间（2588–2590、7834–7836、13081、27125…）；
- 【未测】这些帧是否为"行末 overhead 帧"的 CRC/ECC 载体。
- **判定实验**：取两版 bitstream（仅差 1 个 INIT 位），看 word 50 是否同步变化；若变化 → 该帧含该字段的校验；若不变 → word 50 与数据位无关。
- 影响：本项目此前的"写位回环含 ECC"结论应降级为"写位回环在 864/864 次实验中未被硬件拒绝，未能区分 CRC 与 ECC 的作用域"。

## ⑦ 为什么 CLB 是 36 帧而 INT 是 28 帧

位池算术（【本项目实测】）：

| 项 | CLB | INT |
|---|---|---|
| 数据帧 | 34 | 26 |
| 位池容量 | 34×2×32 = **2,176 位** | 26×2×32 = **1,664 位** |
| 承载内容 | 4×LUT6 INIT(256 位) + 8×FF 属性(≈128 位) + 48×IMUX(640 位) + slice 内 PIP/控制 | 124 个 PIP 家族（各 3..18 源共享 k 位，共 1,598 位） |
| overhead | 2 帧 | 2 帧 |

差值 36 − 28 = **8 帧**，来源于 CLB 比 INT 多两类字段：**INIT 的 4 帧**（4×LUT6×64 位）和 **FF/控制字段的 4 帧**。这也解释了为什么 IMUX 段在两块里位置不同（CLB 在 16..25，INT 的 PIP 池从 0 开始铺满 26 帧）。

36/28 这两个数本身是 **485T 实测**；7 系列其它器件（如 artix7）单个 CLB tile 也是 36 帧 ×101 字——【prjxray】artix7 `segbits_clblm_*.db` 的行数与本项目一致，可作旁证，但**严格说 artix7 的 36/28 是 prjxray 实测，不是 UG470 文档结论**。

## ⑨ 常见误解（≥8）

1. **"帧数 = 列数 × 行数"** —— 错。412×365 = 150,380（tile 数），帧数 50,176；帧是按**配置块**排的，不是按 gx/gy 网格。
2. **"每帧都是 101 字"** —— 在 V7 上数据区是 101 字，但**读回/部分重配置路径与 UltraScale+ 不同**；且"101 字全是用户位"也错（含 overhead/较验位）。
3. "帧号 = 线性 tile 序号" —— 错，块按 clock region 分带，带间有 66 帧空隙。
4. "FAR = 帧号" —— 【推断】不成立，FAR 是分行/列/块的地址编码。
5. "word 50 一定是 ECC" —— 错，本设计 99.7% 的帧 word 50 = 0。
6. "一个 tile 的位池在它自己的帧块里、与邻居无关" —— 错，IMUX 选择位在 CLB 块内、但其**源**在 INT 块内，两处都要读。
7. "配置位都是 1 有效" —— 错，大量位是 sense=0（须为 0），例如 PIP 的 `!` 位。
8. "同 tile_type 的位映射对所有器件相同" —— 部分成立（形状一致），但**位偏移需按块基址重算**，本项目实测 artix7→485T 的偏移差可达数帧。
9. "IDCODE 可省略" —— 本实测 bitstream 明确写 IDCODE=0x03687093，它是判别器件型号最快的指纹。

## 附录 B：命令层是怎么"判"出来的（可复现证据链）

### B.1 为什么要先做字节搜索，而不是从 0 开始按字解析

`.bit` 前面有 **150 字节 ASCII 头**（`;top;UserID=…`），所以从偏移 0 按 32 位大端解析**找不到同步字**：

```
words[0..7] = 0x0090FF0, 0x0FF00FF0, 0x0FF00000, 0x01610025, 0x746F703B, 0x55736572 …
                                                                 ↑ "…op;" "User" 是 ASCII，不是命令
```
字节级搜索 `AA 99 55 66` → **offset = 150**（= 头长度），此后才是字对齐的命令流。这是判断"你的解析入口对不对"的第一道校验：**同步字必须出现在 ASCII 头之后，且 150 % 4 ≠ 0 时不能按字对齐硬切**。

### B.2 指针记账（最强证据）

按 `type1: 前进 1+cnt`、`type2: 前进 1+count` 走完整个流：

| 项 | 值 |
|---|---|
| 总字数 | 5,068,346 |
| 数据区（FDRI）字数 | **5,067,776 = 50,176 × 101** |
| 实质包个数 | 26 个包头 + 24 个寄存器值字 |
| NOP 填充字 | 520 |
| 记账合计 | 5,067,776 + 26 + 24 + 520 = **5,068,346** ✅ 与总字数完全相等 |
| 残余字 | **0**（指针正好落在文件尾） |

**残余为 0 是最强的正确性证据**：如果包头位域、寄存器地址、字数中任何一项解错，指针会要么越界、要么提前停下留下无法解释的残字。

### B.3 "FDRI 只写一次"是怎么判的

三条独立证据：

1. **按寄存器号 0x02 统计包个数 = 1**（不是"看起来只有一段"）：

| 字偏移 | 包头 | 含义 |
|---|---|---|
| 44 | `type1, op=WRITE, reg=0x02, cnt=0` | FDRI 头（cnt=0 表示后接 type2） |
| 45 | `type2, count=5,067,776` | **唯一一次整片写入** |
| 5,067,822 | `type1, reg=0x00 (CRC), val=0x155D1AB` | 突发结束后紧接 CRC 写 |

2. **数量精确整除**：5,067,776 = 50,176 × 101，一个字不多一个字不少。若是两段 FDRI，两段之和必须仍等于这个数，且中间要插入 `FAR`/`CMD(WCFG)` 包头——**实测该边界上没有任何包头**（字 5,067,822 直接就是 CRC 写）。
3. **整段数据区里没有第二个同步字**（`AA995566` 出现次数 = 0），排除"隐藏的第二个子流"。

### B.4 为什么物理上只需要一次

FAR 是**自增**的：写一次 `FAR=0` 后，FDRI 每写 101 字就自动推进到下一帧。整片配置空间是 `[0, 50176)` 的连续区间，所以全芯片镜像 = 一次线性写。

**反例形态（可验证的预测）**：如果出现多段 `FAR ← …` + `CMD ← WCFG` + `FDRI ← …` 的组合，说明是**部分重配置（PR）或多区域写**——此时帧空间不是从 0 开始连续写的。本项目只有全芯片镜像，尚未生成 PR 位流对照，故这条标【推断】。

### B.5 一处实测异常（记录，不解释）

序列里 `FAR ← 0x03BE0000` 出现在 `CMD ← START(0x5)` **之后**，随后是 `MASK/CTL0 ← 0x0501`、`CRC`、`SHUTDOWN`。启动之后再写 FAR 不合常规，可能原因：① 这是"最后 2 个 overhead 帧"的地址；② 本项目对 CMD 0x05/0x09 的名称映射有误。**标【待核】**，验证法：用 Vivado 生成同一设计的 `-bin` 与 `.bit` 对照，或换一个设计看该 FAR 值是否随列位置变化。
