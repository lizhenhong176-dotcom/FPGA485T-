## 1. 位流中的确切位置

### 1.1 文件字节布局（实测）

| 字节区间 | 长度 | 内容 |
|---|---|---|
| 0 – 149 | 150 B | ASCII 头（器件名 `7vx485tffg1157`、构建日期） |
| 150 – 153 | 4 B | 同步字 `AA 99 55 66` |
| 154 – 337 | 184 B | 包序列：TIMER / IDCODE / COR / WCFG / FDRI 头（46 个字） |
| **338 – 20,271,441** | **20,271,104 B** | **FDRI 数据区 = 50,176 帧 × 404 B** |
| 20,271,442 – 20,273,537 | 2,096 B | 尾部：CRC / START / SHUTDOWN 等包 |

推导要点【实测】：
- 同步字按字节搜索命中 **offset 150**（不是 4 字节对齐），所以"头长度 = 150"。
- 同步字之后到数据区之间是 46 个字（184 B）的寄存器写包。
- 数据区长度 = 5,067,776 字 × 4 = 20,271,104 B，且 `5,067,776 = 50,176 × 101`（自检门）。
- 尾部 = 20,273,538 − 20,271,442 = 2,096 B。

### 1.2 两套坐标

| 体系 | 变量 | 用途 |
|---|---|---|
| 逻辑坐标 | `(frame, word, bit)` | 解码/写位时的语义坐标 |
| 文件偏移 | `byte_offset` | 直接读写文件时的物理坐标 |

换算公式【实测验证】：

```
word_index_in_frame = wof(Yr) + parity          # wof(y) = 2*(y%50) + (y%50 >= 25)
byte_offset = 338 + 404 * frame + 4 * word_index_in_frame
             且  bit 落在该 4 字节字的第 bit 位（大端字序内，bit0 = LSB）
```

边界条件：
- `frame ∈ [0, 50176)`，`word ∈ [0, 100]`，`bit ∈ [0, 31]`；
- 越过 `338 + 20,271,104` 即进入尾部包区，不再是帧数据；
- **一个字 = 4 字节，"bit" 不是字节偏移**，写位要对整字做读-改-写。

### 1.3 真实算例（frame 31696，即 `INT_L_X6Y11` 块基址 31680 + frame_off 16）

| 逻辑坐标 | 字节偏移 | 该字内容 | 该位的含义 |
|---|---|---|---|
| (31696, **22** = wof(11)+**0**, bit 26) | 12,805,610 = `0xC365EA` | `0x04000000` | bit26=1 → `IMUX_L11` 的码字（该处解出 `SR1END1`） |
| (31696, **23** = wof(11)+**1**, bit 25) | 12,805,614 = `0xC365EE` | `0x02000001` | bit25=1 → `IMUX_L7` 的码字（该处解出 `SW2END3`） |

两者相差 **4 字节**，同属 `frame_off=16`、同一行 `Yr=11`，但属于**两个不同 mux 的码字**。
计算过程：`404 × 31696 = 12,805,184`；`+338 = 12,805,522`；`+4×22 = 12,805,610`；`+4×23 = 12,805,614`。

## 2. 作用

### 2.1 解码端：parity 是"取哪半个 64 位切片"的开关

1. 由 tile 名算出 `block_base` 与 `Yr = Y % 50`；
2. 对每个 `frame_off`，得到 `frame = block_base + frame_off`；
3. 取 **两个** 字：`w0 = wof(Yr)`（parity 0）、`w1 = wof(Yr)+1`（parity 1）；
4. 把一个 cell 的坐标 `(frame_off, parity, bit)` 映射为：先按 `frame_off` 选帧，再按 `parity` 选 `w0/w1`，最后取第 `bit` 位；
5. 一个家族的多个 cell 全取到后，与码表比对（`ones ⊆ 观测`、`zeros ∩ 观测 = ∅`）。

### 2.2 生成端：写回时按 parity 分派

规则：`word = wof(Yr) + parity`，随即对该 4 字节做读-改-写；**同一家族跨 parity 的 cell 必须分别落到两个字**。
顺序：先定位帧（块基址 + frame_off），再定位字（wof + parity），再改位，最后**重算帧级校验字 word 50 与尾部 CRC**（本项【未测】：CRC/ECC 算法尚未解出，目前只能"生成后读回"验证）。

### 2.3 两类错误

| 错误 | 触发场景 | 后果 |
|---|---|---|
| 把两个字当"内容相同的冗余" | 只读 parity 0 就开始解码 | 统计上漏掉约一半 cell（parity1 侧 6,040 个），家族码集不完整 → 大面积 UNEXPLAINED |
| 漏掉 parity 只用 `(frame_off, bit)` | 从 prjxray 表直接复制坐标却不拆 parity | 一个观测位集匹配多个家族 → AMBIGUOUS 或误判（实测 800 个 `(off,bit)` 里 **798 个**被 ≥2 个家族共用） |

## 3. 来历

### 3.1 外部继承

prjxray 的 segbits 表把一行的 64 位写成 `bit64`，约定 **`bit64 < 32` 为低字、`bit64 ≥ 32` 为高字**，转换式即：

```
bit64 = parity * 32 + bit,   parity = bit64 // 32,   bit = bit64 % 32
```

我们沿用该编号约定（外部继承，未自行定义）。

### 3.2 本项目自测（三条可追溯证据）

1. **S5 差分**：`PRECYINIT` / `AOUTMUX` 的位只落在 `w40`（parity 0），`w41`（parity 1）不动 —— 若两字是冗余，改动必然成对出现【报告 `S5_CARRY_AOUTMUX.md`】。
2. **parity=1 侧独立解码成立**：S9/S24 的 IMUX 码全部落在 parity 1，仍唯一解出 48 个 IMUX，且与 Vivado ROUTE 真值 **6/6 token 一致**；本文算例中 `IMUX_L7←SW2END3` 与 `IMUX_L11←SR1END1` 就是在 parity 1/0 两侧分别解出的【报告 `S9_CSP_DISAMBIG.md`、`S24_IO_WALK_CLOSURE.md`】。
3. **碰撞统计**：只按 `(frame_off, bit)` 索引时 800 个坐标中 798 个被 ≥2 个家族共用；加入 `parity` 后 `(frame_off, parity, bit)` 下 12,168 个 cell 无冲突【`all_cells.json` 全量统计】。
4. **家族不跨字**（2026-11-16 补测）：172 个 INT 家族中 **86 个整族只占 parity 0、86 个整族只占 parity 1，跨两个字 = 0 族**。即"某 mux 的码池落在低字还是高字"是家族的固有属性，不是随机分布 —— 这正是 parity 能消解 798/800 冲突的结构性原因。CLB/BRAM/DSP 侧是否同样【未测】。

一句话分工：**编号约定是外来的，字对是否真实、两字是否独立承载数据，是本项目实测确认的。**

## 5. 三条误解

**误解 1：parity 是校验位。**
纠正：它是"这一位在低字还是高字"的索引（0/1），两字是不同的 32 位配置数据；校验字是 **word 50**，且只在 fabric 块成立（`io72/edge30/CMT/GTX` 块的 word 50 是真实配置字）。

**误解 2：一帧里同一位置只有一个字有用。**
纠正：一帧的 101 个字里，第 0..49 与 51..100 是 50 行的两个字，**每行两个字都承载数据**（该行 tile 的 64 位切片），只有第 50 个字让位给校验。

**误解 3：parity 只影响读取，不影响写回。**
纠正：写回时 `word = wof(Yr) + parity` 是硬约束；写错字会命中同一帧里另一行 tile 的位，导致"改了但没生效"或"改坏了别人的逻辑"。
