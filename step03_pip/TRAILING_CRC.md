# 比特流尾部 32 位值（CRC 寄存器）——未解，记录证据

状态：**未解决**。截至 2026-10-25 21:40，仍无法用任何标准/常见 CRC 变体复现 bitgen 写在
`0x30000001` 后面的 32 位值。

## 1. 位置与结构（已确认）

以 `/opt/lzh/step03/lutmap/v_0000000000000000.bit`（20,273,538 B，INIT=0 基准）为例：

| 偏移 | 内容 |
|---|---|
| 338 | FDRI 载荷起点（50,176 帧 × 404 B = 20,271,104 B） |
| 20,271,442 | 载荷结束 |
| 20,271,442 | `0x30000001`（写 CRC 寄存器） |
| 20,271,446 | **crc1 = 0x5F3586D1** |
| 20,271,450 … | NOP `0x20000000` 若干 |
| 20,271,458 | `0x30008001` + `0x0000000A`（DESYNC） |
| … | `0x3000A001` + `0x00000501`（COR1） |
| 20,271,914 | `0x30000001` |
| 20,271,918 | **crc2 = 0xE3AD7EA5** |
| 20,271,922 … 文件尾 | NOP 填充（约 1,616 B） |

注意：文件长度比"载荷 + 命令"多出 1,616 B 的 NOP，所以**文件最后 4 字节是 0x20000000，不是 CRC**；
早先脚本把"文件末 4 字节"当 CRC 是错的，已修正为按 `0x30000001` 定位。

## 2. 已确定的映射（与 CRC 无关，已独立验证）

X10Y10 的 A6LUT，INIT 64 位 ↔ (帧, 字, 位)：

```
k ∈ [0,63]
df  = 2*(1-((k>>3)&1)) + (k&1)        # 帧 = 31748 + df
bit = 15 - 4*(k>>4) - ((k>>1)&3)      # 字 20
```

每改一位 INIT，同一帧的 word 50 的低 13 位（ECC）随之变化。这 64 组
(data bit, ECC 掩码, crc1) 采样在 `step03_pip/lut_crc.json`（11 KB）。

## 3. crc1 与载荷的关系：线性但算法不明

用 64 个变体的 crc1 与基准相减得到 64 个"增量"。增量是**线性**的（同一位在不同帧上
贡献一致，ECC 掩码也能被一致地解出），所以它确实是一个对载荷做 GF(2) 线性变换的校验值。

但以下所有组合都**不等于** crc1（载荷 = 文件 338 … 20,271,442）：

| 处理方式 | 结果 |
|---|---|
| CRC-32/MPEG-2（poly 0x04C11DB7，MSB，init FFFFFFFF，xorout 0） | 0xDA126516 |
| 同上，xorout FFFFFFFF | 0x25ED9AE9 |
| 同上，init 0 | 0x76F494AF |
| CRC-32/ISO-HDLC（zlib，reflected，init/xorout FFFFFFFF） | 0x8869EB93 |
| 同上，xorout 0 | 0x7796146C |
| 同上，init 0 | 0xEA197359 |
| CRC-32C（0x1EDC6F41）× 6 种参数 | 0x9145F5 / 0x53A996 … 均不等 |
| CRC-32/BZIP2、POSIX、XFER(0xAF)、0x741B8CD7、0xA833982B、0x814141AB、0xF4ACFB13 等 × 6 参数 | 均不等 |
| 整字字节序反转（LE words） | 0xFD6FDD87 / 0xD249864A |
| 字内位序反转（bitrev32） | 0x5261924B / 0xE1BBF6BF |
| 16 位半字交换 | 0x155ED23B / 0x6D5CBF82 |
| 帧内字序反转 / 帧序反转 / 两者 | 均不等 |
| 去掉 word50（每帧 400 B） | 0x9A631646 / 0x3A73C297 |
| 整个文件（0 … 载荷末）| 0xC6D11C94 / 0xD6EA655B |
| 从 sync(334) / FDRI 命令(330) 起 | 0x6E72FAF6 / 0xF795F24D |
| zlib CRC-32 扫描所有起始偏移 0…459（× 4 种结束位置） | 全部不命中 |
| md5 / sha1 / sha256 取前 4 字节 | 不等 |
| 输出位反转（refout 变体） | 不等 |

另外做过的排除：`lut_crc.json` 里 word50 在基准中本来就是 0，所以"清 ECC 位"和
"整个 word50 清零"得到同一个 CRC，说明这个基线里 ECC 位为 0，不是"跳过 ECC"能解释的差异。

## 4. 结论与影响

- crc1 是 bitgen 内部的校验值，**不是**标准 CRC-32，也不是常见哈希。
- 因此"只改载荷、保留原 CRC"这条路在原理上就是错的：改动后设备算出的 CRC 与原值不符。
- 需要说明的风险：如果 7 系列在配置阶段校验该寄存器（STAT.CRC_ERROR），我们生成的
  比特流会被拒绝，DONE 不拉高。**本地/远端都没有 JTAG 下载器（lsusb 为空），无法实测**。
- 反过来说，如果该值只用于 RCRC 回读校验、配置阶段不比较，则保留旧值可以工作——
  这一点必须用硬件验证才能定论。

## 5. 可选路线（需要决策）

1. **硬件验证**：拿到一块 VC707/VC709 + JTAG，烧一个只改 INIT、CRC 不更新的比特流，
   看 DONE 是否拉高。这是唯一能判定"CRC 是否必须"的实验，成本最低、结论最硬。
2. **逆算法**：把 crc1 当作未知 GF(2) 线性映射，用更多 Vivado 变体（例如 100 个随机
   INIT）解出 116 个"位贡献列"，在本站点做出**查表式** CRC 更新。缺点：绑定站点，
   换 LUT/换帧就失效，不能推广。
3. **绕过**：不在比特流层写，而是保留 DCP、用 Vivado `write_bitstream` 重新生成
   （现状的 imux/LUT 实验流程就是这样做的）。可靠但没有"纯比特流改写"能力。
4. **继续猜**：把候选空间扩到"每帧 101 字中 ECC 字位置不同 / 帧内 32 位字重排 /
   与 FAR 交织"等硬件布局假设。收益不确定。
